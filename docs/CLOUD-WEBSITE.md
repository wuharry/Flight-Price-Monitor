# 叔叔使用的雲端查價網站

網站沿用 GitHub Pages、Supabase 登入與資料庫，由私人 Apify Actor 執行 Google Flights 查價。每日排程使用 Apify 原生雲端排程，不依賴管理員或使用者電腦，也不使用 Codex 本機自動化或 Google Cloud 付費服務。

## 使用方式

1. 用原本已驗證的 Email 與網站密碼登入。
2. 填好機場、去回程日期、成人人數、通知價格門檻，勾選「啟用此行程」並儲存。
3. 每天台北時間 **08:00、11:00、14:00、17:00、20:00、23:00** 各查一輪已啟用行程，每輪約 20 分鐘；00:00～08:00 不查。符合條件才寄信。電腦與網頁可關閉。
4. 全部受邀帳號合計有 5 條以下符合資格的行程時，每條每輪查一次、每天最多 6 次；超過 5 條時，每輪由最久未嘗試的行程優先，輪流查 5 條，每條每天次數相應減少。
5. 需要當下票價可按「立即查價」；每天另保留最多 2 次手動額度。手動或失敗的嘗試會占用當輪。
6. 停用行程可停止之後的排程；已經開始的這一次工作可能仍會完成。新增或修改行程不會立刻寄信，會等待下一個符合資格且有容量的時槽。

網站只在伺服器確認排程已開通時顯示「每日自動查價」。無法讀取狀態、帳號未獲邀或尚未啟用時，不會臆測排程正在運作。通知顯示「寄件服務已接受」只代表 SMTP 接受，仍需收件人查看收件匣與垃圾郵件。

價格為 Google Flights 選定的台灣虎航直飛行程之含稅參考總價，不保證是所有組合最低價，也未確認為 tigerLight；來源可能延遲最多約 24 小時。票種、行李、選購與實際可售價格以航空公司結帳頁為準。舊來源與新來源的歷史分開比較。

## 每日排程與資料隔離

Apify 原生排程每天在 08:00、11:00、14:00、17:00、20:00、23:00 各一輪，每輪在整點及 :05、:10、:15、:20 共 5 個時槽（Asia/Taipei）啟動同一個私人 Actor。cron 為 `0,5,10,15,20 8,11,14,17,20,23 * * *`，時區固定 `Asia/Taipei`。每次只選取一條啟用、日期未過期、擁有者已驗證且同時在資料庫與 Runtime 允許名單的行程。找不到符合條件的行程就快速結束，不開啟查價瀏覽器、不寄信。

每條行程每輪最多一次任何來源的嘗試，每天最多自動 6 次。行程多於每輪 5 個時槽時，由最久未嘗試的行程優先，各行程輪流。網站顯示的「每條每天最多次數」依資料庫允許名單內、已驗證擁有者的啟用 Google Flights 未過期行程總數計算：5 條以下為 6 次，超過 5 條為 30 ÷ 條數（無條件進位），不會因個別 worker 的 Runtime 名單較少而改變。每輪的紀錄區間從該輪開始前 1 小時起算：08:00 輪為台北 00:00 起至 10:00 前，之後各輪依序從 10:00、13:00、16:00、19:00、22:00 起至下一區間前；實際啟動時間仍只有上述時槽。

輸入只有 action=scheduled-check、provider=google-flights；航線、收件人和所有權都從資料庫讀取，不接受輸入任意收件人或搜尋條件。工作先原子預約再 claim，一次最多查一條，失敗、過期及回應不明仍計次，不會在同一輪自動重試同一條。手動查價亦共用這份紀錄。選取順序為尚未嘗試優先，其次依最近一次嘗試由舊到新排序。

行程若有最近 23 小時建立的 pending 通知，排程會先跳過，避免寄件結果不明時由之後的輪次自動重寄。滿 23 小時後才可再次自動查價，由既有通知流程處理過期紀錄。此新增限制只影響自動排程；手動查價流程不變。

排程最多同時一個、手動最多同時一個，不同規則可並行；同一規則不可同時執行。網站 worker 使用規則範圍的鎖與資料存取，既有全規則監控鎖也會互相排斥。通知只寄給目前擁有者的已驗證信箱。

目前只開放叔叔帳號，網站每帳號最多 10 條規則。每日共 30 個時槽（6 輪 × 5），5 條以下每輪各查一次；6～10 條每輪輪流查 5 條，每條每天約 3～5 次。手動嘗試、通知等待、失敗、服務中斷或額度不足仍可能使部分行程當天未查完。若日後增加其他帳號，這些時槽與額度會共用，必須重新規劃容量；不應宣稱任意帳號數都能每天查完。

## 不產生額外帳單的條件

- Apify 保持 **Free、沒有付款方式、不升級**；免費額度耗盡由平台阻擋服務，不加購續跑。Supabase 與公開 GitHub Pages 也維持免費方案。
- 每個 Actor run 固定 1 GB、180 秒上限，不設定錯誤後重啟，不啟動子 Actor。
- 自動最多 30 次／台北日、930 次／預算區間；手動最多 2 次／日、62 次／預算區間；總上限 32 次／日、992 次／預算區間。區間為「今天及前 30 個台北日期」，從最早日期的台北 00:00 起算，跨曆月不重置，也不受排程啟動秒數或伺服器時區影響。失敗、等待過期、未知回應都不退還，刪除規則也不會刪除已消耗額度。
- 30 個固定排程時槽（含沒有行程的空工作）及每日 2 次手動工作，若全部用滿 1 GB × 180 秒，31 天運算約 US$9.92，超過 Free 每月 US$5 額度；依 2026-10-19 實測每次約 30 秒推估約 US$1.7，另有建置、資料儲存及流量。這只是運算估算；額度用完時 Free 平台會停止執行到下一帳期，期間不查價也不扣款。真正不產生額外帳單仍依靠 Free 的平台阻擋；其他專案工作也會共用帳戶額度。

免費服務可能暫停、故障或額度耗盡，屆時當天查詢可能未完成；不會為補跑而升級或扣款。Supabase Free 也可能因低活動暫停，需管理員恢復。

## 管理員部署順序

1. 備份目前規則與工作紀錄。依序套用 schema.sql、multi-user.sql、cloud-check.sql、daily-check.sql；新排程設定預設關閉，允許名單預設空白。瀏覽器不能寫工作、預算、鎖或排程設定。
2. 將排程允許的已驗證帳號放入私人資料庫 cloud_monitor_settings.allowed_emails 與 Actor Runtime SCHEDULE_ALLOWED_EMAILS；既有 Supabase、Gmail 憑證只留在加密後端，不能套用到建置環境、網站或公開紀錄。
3. 建置 Actor，保留 1 GB／180 秒並固定成功 build。Actor 預設 Input 與排程 Input 都改成最小的 scheduled-check＋google-flights，避免舊 search 範例被平台合併。保留手動網站 worker 與原有 check 等入口。
4. Edge Function cloud-check 繼續驗證使用者 JWT、信箱與規則所有權，並將 APIFY_CLOUD_CHECK_BUILD 固定到新版。手動預約的新限額由 SQL 統一執行。
5. 發布網站；登入後以 get_cloud_schedule_status RPC 讀取實際啟用狀態。Supabase Auth Site URL／Redirect URLs 仍為完整 Pages 網址（含專案路徑與結尾 /）。
6. 建立原生排程，cron 為 `0,5,10,15,20 8,11,14,17,20,23 * * *`、timezone 為 `Asia/Taipei`，指定成功 build、1024 MB、180 秒、restartOnError=false。核對 Console 的 Next runs 為每天 6 輪、合計 30 個時槽後，才開啟資料庫排程設定。
7. 用原生排程立即執行一次，確認只查一筆、結果回寫、通知按條件處理；沒有符合規則時必須成功 no-op。由收件人另外確認實際送達。

要全局停止時，同時停用原生排程與 cloud_monitor_settings.enabled。叔叔只需在網站停用個別行程。舊 GitHub Flight monitor workflow 的 MONITOR_ENABLED 維持未設定，避免雙重排程。

## 改為每 3 小時一輪

2026-10-19 程式改為每天 6 輪。已部署的資料庫與原生排程在套用前仍是早晚兩輪。網站同時接受新舊兩種排程狀態，先部署網站，就不會短暫顯示「狀態未知」。

1. 部署網站：推送 main 後由 GitHub Actions 發布。
2. 在 Supabase SQL Editor 依序重新執行 cloud-check.sql、daily-check.sql。兩者都可重複執行，不清除工作紀錄，也不改動 cloud_monitor_settings 的啟用狀態與名單。
3. 在 Apify Console 將原生排程的 cron 改為 `0,5,10,15,20 8,11,14,17,20,23 * * *`，時區維持 `Asia/Taipei`，其餘設定不變；核對 Next runs 為每天 6 輪、合計 30 個時槽。Actor 不需重新建置。
4. 登入網站，確認顯示「每日自動查價已啟用｜每天 6 輪」。

後兩步的先後不影響額度或重複查價：資料庫仍是兩輪時，新排程多出的時槽會因當輪已查過而 no-op；排程仍是兩輪時，新資料庫只在 09:00、21:00 查價。
